Состав M-50 — инженерная цель fixture, не пользовательский лимит модулей. Задача B-03 создаёт физически допустимую фиксированную раскладку в новой схеме с этим составом или документирует корректировку числа элементов до начала benchmark. Нельзя менять состав между сравнениями скорости незаметно. У каждого fixture сохраняются hashes, число сегментов/примитивов, параметры окружения, маршруты камеры, draw calls/треугольники и версии.

Фиксированные fixtures создаются независимо от нового генератора; иначе его дефект может одновременно испортить вход и ожидаемый результат. Старое отслеживаемое приложение удалено по решению пользователя; baseline старой версии не является обязательной предварительной задачей. Измерения новой версии фиксируются независимо, старый импорт не реализуется.

## Производительность

| Проверка | Начальная цель | Метод |
|---|---|---|
| PERF-01 / PF-01 | ПК M-50: целевые 60 FPS, p95 frame interval ≤20 мс | 2 минуты прогрева, 10 минут маршрута, все кадры, отдельно паузы/GC |
| PERF-02 / PF-02 | Android M-50: цель 60, допустимый минимум 30 FPS, p95 ≤35 мс | Физическое устройство, APK, те же виды/условия, запись нагрева и частоты экрана |
| PERF-03 / PF-03 | ПК p95 input→preview ≤100 мс | 1000 pointer events по фиксированному жесту, три размера карты, worker занят |
| PERF-04 / PF-04 | L-1000 первая полезная страница ≤1 с | 10 холодных и 10 повторных открытий; показывать median/p95; отдельный замер старта приложения |
| PERF-05 / PF-05 | M-50 до готовности прохождения ≤3 с | 10 открытий, отдельно холодные ресурсы/шейдеры и тёплый кеш |
| PERF-06 / PF-06 | UI-реакция на cancel ≤100 мс; job прекращён ≤500 мс | Отмена на каждом этапе, включая boolean/финальную валидацию |
| PERF-07 / PF-07 | Checkpoint не создаёт main-thread task >50 мс | W-60 и реальное прохождение с сохранениями, трейс long tasks и запись размера сообщений |
| PERF-08 / PF-08 | Нет накопления ресурсов за 20 открытий | После прогрева renderer.info geometries/textures возвращаются к фиксированному базовому уровню; JS heap после GC не имеет монотонного роста, медиана последних 5 ≤110% первых 5 |
| PERF-09 | M-100 не зависает и не падает, отменяемые операции сохраняются | Отдельный отчёт, без заявления того же FPS, что для M-50 |
| PERF-10 | Первый допустимый вариант и полный запрос измерены отдельно | 10 фиксированных seed M-50, requestedVariants=3, watchdog=60с; записать долю complete/exhausted/timeout, а не только успешные попытки |

Для PERF-10 цель первого релиза: хотя бы 8 из 10 контрольных запросов default-профиля дают 3 полностью проверенных варианта в 60 секунд на тестовом ПК; 2 оставшихся обязаны закончиться определённым статусом без блокировки UI. Это цель качества генерации на согласованном наборе, не гарантия для произвольных контуров. Низкое покрытие не повышает success rate, если мягкая цель не выполнена. Набор и критерии фиксируются до настройки алгоритма; отдельный набор seed используется для регрессии.

Все измерения указывают CPU/GPU/RAM, ОС, браузер/WebView, разрешение экрана и canvas, DPR, частоту дисплея, версии приложения/профилей и hashes. Модель телефона выбирает исполнитель; отсутствие доступного физического устройства отмечается как невыполненная мобильная приёмка. Не заменять её headless или desktop device emulation.

Синтетический performance-тест не измеряет комфорт пользователя. Стандартные CPU/GPU-профайлеры применяются для диагностики провала бюджета; после исправления повторяется затронутый сценарий, а не все проверки без причины.

## Визуальная приёмка VIS-01

Задать целевые сцены сохраняемого вида: чёрная/цветная ткань, близкое просвечивание и контровой свет, крыша включена/выключена, каркас/укосины, лес и солнце, день/низкое солнце. Зафиксировать положение камеры, время/окружение и material settings. Углы: внутри, вдоль стены, перекрёсток, снаружи, под крышей. Новые круг/треугольник используют те же материалы и элементы конструкции.

Снятие старых скриншотов до удаления отменено пользователем. Если старые изображения уже доступны, использовать их с указанием происхождения; иначе проверить полный перечень визуальных свойств вручную и зафиксировать новые эталонные сцены. Это не доказывает точное совпадение со старой версией без старых изображений. Последующие сравнения выполнять на том же устройстве, backend и разрешении. Автоматически проверять наличие объектов/материалов, положение силуэтов/проёмов и отсутствие света через закрытую стену. Pixel diff выдаёт карту различий для проверки, но не единственный критерий из-за различий GPU. Ручная проверка фиксирует отсутствие пропавших элементов, изменившегося просвета ткани, ориентационных подсказок и заметных швов. Изменение цвета/освещения по ошибке не объявляется оптимизацией.

Графический gate: одновременно проходят VIS-01 и PERF-01/02. Если не проходят, задача R-03 получает конкретный CPU/GPU bottleneck и следующую ограниченную гипотезу оптимизации. Полный отказ от требуемого эффекта требует изменения продуктового требования пользователем.

## Функциональные уровни проверок

- Unit/property: схема, нормализация, PRNG, контуры, проёмы, физические инварианты, immutable hashes, state machines. Генеративные проверки используют фиксированные seed и сохраняют минимальный контрпример.
- Integration: worker revisions/cancel, IndexedDB atomicity и fault injection, JSON round-trip без каталога, последовательность chunks. fake-indexeddb не заменяет реальный WebView/браузер.
- Browser E2E: библиотека→просмотр→слепое прохождение→запись, редактор→генератор→варианты, import conflicts и восстановление. Использовать доступные роли/labels; не привязывать проверки к внутренней структуре React.
- Physical APK: установить, без сети импортировать карту, пройти, свернуть/вернуть, перезапустить, экспортировать, обновить APK поверх новой версии с тем же ключом; подтвердить сохранение новой библиотеки.

## Сценарии отказов

FAIL-01: заполненное хранилище/QuotaExceeded при save или checkpoint → ясная ошибка, последний коммит доступен, очередь ограничена.

FAIL-02: отмена импорта в staging/повреждённый файл/unknown primitive → рабочая библиотека не меняется.

FAIL-03: worker падает или возвращает старую ревизию → проект доступен, результат не применяется, retry возможен.

FAIL-04: WebGL context lost/background Android во время движения и записи → пауза без скачка, подтверждённые chunks доступны, сцена восстанавливается.

FAIL-05: принудительное завершение между записью chunk и terminal state → восстановление сессии из последнего коммита, finish не выдумывается.

FAIL-06: огромный JSON или дуга с чрезмерной сегментацией → лимит проверяется до крупных выделений памяти, интерфейс остаётся доступен.

## Выпуск и доказательства

Первый рабочий выпуск допускается после GEO, RUN/DB/REC/IO/UX, GEN, VIS и PERF-01…08 на целевых платформах, плюс отчёт PERF-09/10 и APK-сценарий. Проверки агентной модели — отдельный gate исследовательского этапа.

Артефакты результата задач: `reports/` (JSON с метриками, hashes, версиями и устройствами), trace/screenshot по необходимости, перечень команд запуска. Большие бинарные traces не коммитятся автоматически. В документации различаются pass/fail/not-run; отсутствие оборудования или данных не записывается как pass.

Для начала реализации эти артефакты ещё не нужны: нужны исполнимые задачи их получения, которые перечислены в [tasks.md](tasks.md).
